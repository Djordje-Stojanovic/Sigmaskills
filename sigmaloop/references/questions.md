# The question round

One message, numbered, at most 10. Each item gives the question, then two clear options — `Recommended: <best default>` and `Alternative: <strong second option>` — with a few words of why, drawn from step 1. Option 3 is always the user's own custom answer (no hardcoded rules). The user can reply "all recommended", pick `Alternative`, or give a custom answer for any number. Ask only what the repo cannot answer; state a fact the repo gives instead of asking it.

## The ten

1. **Speed metric.** What counts as one accepted unit, and what rate do we watch? `Recommended:` accepted units per hour and per million tokens (drafted work counts zero until accepted). `Alternative:` accepted units per hour only (when token cost is flat or unmeasured).
2. **Slots & max parallel workers.** How many parallel workers run at once? `Recommended:` 5–6 slots with isolated workdirs/worktrees (capped by CPU cores and independent queue items; a repo rule wins). `Alternative:` 2–3 slots for a smaller queue, or solo for fewer than 5 independent units or a host that cannot start agents.
3. **Models per role.** Which models and effort run planner, builder, reviewer, and taste, chosen from the host's live capabilities (or the repo's model file)? `Recommended:` top-tier planner, cheap/mid builders, a mid/top reviewer from another provider than the builder (one per finished work package, no cap), and a taste/visual model when UI or media is in scope; effort from the repo's rule, else high (lowered where checks still pass). `Alternative:` single-provider mid-tier across builder and reviewer when only one provider is configured or quota-safe.
4. **Machine, Colab VM count, harness and start.** Which machine runs the work and heavy builds, and how does the harness run? Google Colab offers cheap standard low-RAM or High-RAM VMs so heavy builds stay off the owner's PC; ask which harness only when SKILL.md step 2 could not tell. `Recommended:` 2 Google Colab High-RAM VMs for heavy builds, harness run-to-done (`/goal` where it exists) in this session, no wake task, no cron. `Alternative:` 0 Colab VMs (local-only on this PC or another owned machine) or 1 light Colab VM, with a clock wake or plain instruction if the harness has no run-to-done.
5. **Stop line.** The one command whose printed output proves done, and/or a time and zone. `Recommended:` the tracker's own status command plus a time cap. `Alternative:` time cap only (stop at a fixed wall-clock time and write the handoff).
6. **Scope and order.** The ranked list (id, line, size; show the first 10 and a count). `Recommended:` value first, then unblocking power; blocked and user-live items last. `Alternative:` shortest-unblocker-first (clear small foundational items before larger vertical slices).
7. **What may be deleted.** Records, checks, gates and scaffolding the run may cut. `Recommended:` records no machine reads, checks that never caught anything, and gates that never passed; nothing in user content. `Alternative:` keep existing gates and scaffolding untouched and cut only scratch files created by this run.
8. **Limits.** The owner's orders (his sentence and its date for each), mechanical guards (the fault each prevents), and scope notes (what no ticket covers; a note, not a ban). `Recommended:` protect user-live items, other agents' work, production data, and irreversible deletes of data. `Alternative:` stricter repo-scoped guard (also freeze specific shared files or directories the owner names).
9. **Pre-authorised actions and budgets.** Commit, push, PR, merge, deploy, delete merged branches and worktrees, close tickets; and each spend limit (what, amount, period, accounts, meter command). `Recommended:` all except deploy (deploy only when the repo names a deploy step); no meter, no budget. `Alternative:` stop at ready PRs (`sigmaship stop` — no merge, no deploy) or set a per-account spend cap with a meter command.
10. **Checkout, PR strategy, architecture & inner-loop cadence.** How workdirs, PRs, module structure, tests, reviews, and retries work per cohesive vertical work package. `Recommended:` isolated worktrees/workdirs + 1 feature branch and 1 PR for all tickets; decoupled crates/modules with a flat dependency graph (max depth 2); fast `< 2s` unit tests (`new test LOC <= src LOC`; heavy full-corpus checks in dedicated gates only); max 2 review rounds (clean round ends it; fix P0–P2, drop style nits) then fix and land; park after 3 failed fix tries; builder ticks its own box with evidence; stuck after 30 minutes with no commit or output. `Alternative:` PR-per-ticket (or 1 shared checkout committing by path) and a monolith/single-crate layout for tiny projects, with heavier per-ticket checks or 1 review round.

## After the reply

- Take the recommended answer for any blank and log it as `Ruling: <what> - <why> - <cost if wrong>`.
- A pre-authorisation the user did not give is not given: write "ask" for it.
- A reply that contradicts the repo wins; log the conflict as a ruling.
